# AGENTS.override.md

## 1. 文档定位

本文件用于约束代理在 `cloud-bridge/` 目录内工作的方式。

`cloud-bridge` 是 Bridge 服务端模块，承担控制面核心职责，通常涉及：

- Agent 接入
- 路由与资源调度
- 会话协同
- 管理台前后端
- 配置与运行时装配

在本目录内工作时，必须优先关注：

1. 服务端行为稳定性
2. Agent/Bridge 协同兼容性
3. 配置兼容性
4. 管理台前后端契约一致性
5. 不破坏既有运行语义

---

## 2. 模块边界认知

### 2.1 目录职责
主要目录含义如下：

- `cmd/cloud-bridge/`：程序入口与装配
- `runtime/bridge/`：Bridge 核心运行时
- `web/`：Bridge 管理界面前端与嵌入资源
- `config.example.yaml`：配置示例

### 2.2 边界原则
在本模块内工作时：

- Bridge 服务端逻辑优先留在 `runtime/bridge`
- 管理台前端逻辑优先留在 `web/`
- 协议与通用抽象优先遵循 `ltfp/`
- 针对公共方法优先留在 `pkg`
- 不把只属于 UI 的逻辑写进 Bridge 运行时
- 不把服务端运行策略藏在前端页面里

---

## 3. 工作原则

### 3.1 先判断任务性质
修改前先判断是：

1. Bridge 核心运行时问题
2. 路由/资源分配问题
3. 会话/认证/接入问题
4. 配置问题
5. 管理台前端问题
6. 前后端联动问题

其中第 1、2、3、6 类默认按高风险处理。

### 3.2 不做无关行为变更
不要为了代码整洁而顺手改变：

- 默认配置行为
- Agent 接入语义
- 路由分配行为
- 管理台状态含义
- 对外返回结构

---

## 4. `runtime/bridge` 高风险规则

### 4.1 核心运行时属于高敏感区
修改 `runtime/bridge` 时，必须特别检查：

- Agent 接入行为
- 会话建立/解绑
- 路由分配
- 状态同步
- 认证与鉴权
- 超时、重试与清理

### 4.2 若涉及 Agent/Bridge 协议边界
必须显式说明：

1. Bridge 侧改了什么
2. Agent 侧是否需要同步
3. `ltfp/` 是否需要同步
4. 是否会影响旧版本 Agent

### 4.3 对认证/会话/状态类问题保持谨慎
若改动涉及：

- session
- epoch
- auth
- handshake
- route assign
- reconnect
- full sync

必须关注：

1. 是否存在竞态
2. 是否存在重复提交
3. 是否存在旧连接残留状态
4. 是否存在跨会话污染
5. 是否会在异常恢复后产生错误归属

---

## 5. 配置文件规则

### 5.1 `config.example.yaml` 视为高敏感配置文档
除非任务明确要求，否则不要随意修改配置结构、字段名称或默认值语义。

### 5.2 修改配置时必须说明
若确需修改，必须说明：

1. 新旧字段差异
2. 是否向后兼容
3. 是否需要迁移
4. 是否影响已有部署
5. 文档是否同步更新

---

## 6. `web/` 前端规则

### 6.1 `web/` 是独立前端项目
在该目录内工作时，应先识别：

- 页面问题
- 状态管理问题
- API 契约问题
- 构建嵌入问题

### 6.2 UI 改动原则
- 优先复用现有布局和组件风格
- 不因局部需求做整套视觉重构
- 管理台优先强调可读性、可操作性和状态清晰
- 状态页、表格页、配置页应优先保证信息准确而非炫技

### 6.3 API 联动规则
若修改前端与后端接口联动：

- 必须确认字段是否真实存在
- 不要擅自改接口字段名
- 不要在前端“猜测”后端语义
- 若契约变更，必须同步说明后端影响

### 6.4 `embed.go` 相关规则
若修改影响前端嵌入资源：

- 检查构建输出路径是否变化
- 检查嵌入逻辑是否仍然有效
- 检查测试是否需要同步更新

---

## 7. 构建与产物规则

### 7.1 不直接修改产物目录
默认不要直接修改：

- `web/dist`
- `web/node_modules`

### 7.2 不伪造构建结果
若页面改动依赖构建产物更新，应说明是否实际执行了构建。  
不要把“理论上可构建”表述成“已验证”。

---

## 8. 测试与验证规则

### 8.1 Go 侧验证
涉及 `runtime/bridge` 或入口修改时，优先考虑：

1. 目标包测试
2. `cloud-bridge` 模块内 `go test ./...`
3. 必要时做入口构建验证

### 8.2 前端验证
涉及 `web/` 时，应先查看 `package.json` 中已有脚本，再决定是否运行：

- lint
- test
- build

### 8.3 前后端联动修改
若修改涉及前后端契约或状态流，输出中要明确说明：

- 是否仅改前端
- 是否仅改后端
- 是否需要联调
- 是否未执行联调

---

## 9. 文档同步要求

若改动影响以下内容，应考虑同步更新仓库根 `docs/`：

- Bridge 管理后台方案
- SSE 协议
- Agent/Bridge 技术方案
- 安全与认证设计
- 多 Agent 服务模型
- 实施清单和进度文档

---

## 10. 完成任务后的输出要求

至少说明：

1. 修改目标
2. 影响目录
3. 是否涉及 Bridge 运行时、配置或管理台
4. 核心改动
5. Agent/Bridge 兼容性风险
6. 已执行验证
7. 未执行的联调或部署验证项

---

## 11. 明确禁止的行为

禁止：

- 未说明兼容性就改 Bridge 接入语义
- 未说明原因就改配置结构或默认值语义
- 前端字段与后端契约不一致却不指出
- 直接修改 `web/dist` 或 `web/node_modules`
- 用大规模重构覆盖局部问题
