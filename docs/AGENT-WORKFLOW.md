
# AGENT-WORKFLOW.md

## 1. 文档目的

本文件用于定义本项目中“人类研发人员 + AI 代理”协同工作的统一流程。

目标不是让 AI 替代研发判断，而是让 AI 在明确边界、明确上下文、明确验证标准的前提下，稳定参与以下工作：

- 技术方案分析
- 代码实现
- 局部重构
- 测试补充
- 文档同步
- 评审与风险识别
- 前后端协同实现

本文件适用于本仓库下的主要模块：

- `ltfp/`
- `agent-core/`
- `cloud-bridge/`
- `apps/dev-agent/`
- `service-registry/`
- `docs/`

---

## 2. 工作流总览

统一工作流分为六个阶段：

1. 任务进入
2. 边界分析
3. 方案规划
4. 实施修改
5. 验证确认
6. 文档同步与结果总结

其中：

- 低风险任务可简化流程
- 中高风险任务必须完整走通分析与规划阶段
- 涉及协议、状态机、安全、跨模块联动时，必须参考 `PLANS.md`

---

## 3. 参与角色

### 3.1 人类研发人员
负责：

- 定义业务目标
- 判断优先级
- 决定是否接受风险
- 决定是否发布
- 对关键架构问题作最终判断

### 3.2 AI 代理
负责：

- 快速理解代码与文档上下文
- 辅助分析影响范围
- 提供实施建议与候选方案
- 进行局部实现、补测试、补文档
- 做结构化总结
- 暴露不确定性，而不是掩盖不确定性

### 3.3 协同原则
AI 代理应被视为“高执行力、低上下文自治权”的协作者，而不是可以无限扩张边界的自主系统。

换言之：

- AI 可以做很多事
- 但 AI 不应擅自扩大任务范围
- AI 不应在高风险边界上替代最终架构判断

---

## 4. 阶段一：任务进入

### 4.1 任务输入来源
任务通常来自：

- 缺陷修复
- 新特性开发
- 技术方案落地
- 协议演进
- UI 实现
- 文档评审
- 兼容性修复
- 测试补全

### 4.2 任务输入的最低要求
一个合格任务至少应说明：

- 想解决什么问题
- 大致影响哪个模块
- 是否已有设计文档
- 是否期望只分析、不改代码，还是允许直接实现

若信息不足，优先补足目标与边界，而不是直接编码。

---

## 5. 阶段二：边界分析

这是整个协同流程中最关键的一步。

### 5.1 首先判断任务类型
任务默认分为三类：

#### A. 低风险单点任务
例如：

- 小 bug 修复
- 注释或文档修正
- 局部测试补充
- 单模块、小范围逻辑修正

#### B. 中风险模块内任务
例如：

- 一个模块内部的中等修改
- 某一层实现逻辑调整
- 某个页面或某个运行时分支修复

#### C. 高风险跨边界任务
例如：

- 协议变更
- Agent / Bridge 协同变化
- 认证与安全设计
- transport、状态机、协商、回退逻辑调整
- Tauri 与 Agent Core 通信模型变化
- 前后端契约变化
- 多模块联动实现

### 5.2 识别边界
分析时至少要回答：

- 目标模块是哪个
- 会不会影响其他模块
- 是否涉及文档约束
- 是否涉及测试矩阵
- 是否需要联调
- 是否存在兼容性风险

### 5.3 必读上下文
根据任务类型，优先阅读：

- 根 `AGENTS.md`
- 模块级 `AGENTS.override.md`
- `PLANS.md`
- `docs/` 下对应设计文档
- 目标模块中已有测试与 README

---

## 6. 阶段三：方案规划

### 6.1 何时必须做计划
满足以下任一条件时，必须先写计划：

- 跨模块
- 涉及 `ltfp/`
- 涉及 Agent/Bridge 协同
- 涉及本地通信
- 涉及配置结构
- 涉及兼容性
- 涉及高风险运行时逻辑

具体按 `PLANS.md` 执行。

### 6.2 规划时的输出要求
规划至少要明确：

- 目标
- 非目标
- 影响范围
- 风险点
- 实施步骤
- 验证计划

### 6.3 小任务的简化方式
低风险任务可以不单独写计划文件，但在执行前至少应有一个简要思路：

- 问题在哪
- 准备怎么改
- 准备怎么验证

---

## 7. 阶段四：实施修改

### 7.1 实施前规则
开始修改前，应确认：

- 当前修改范围是否清晰
- 是否已经读取必要文档
- 是否明确不该碰的目录
- 是否清楚生成产物与源文件的区别

### 7.2 实施中的行为准则
默认遵循以下规则：

- 优先最小改动
- 优先局部修复
- 优先兼容式改动
- 不做无关重构
- 不把复杂问题用“顺手重写”掩盖

### 7.3 对不同模块的特别要求

#### `ltfp/`
必须谨慎处理：

- 协议结构
- 状态机
- transport
- 协商/回退
- 兼容性
- 测试矩阵

#### `agent-core/`
必须谨慎处理：

- 长连接
- 生命周期
- 协议探测
- 错误恢复
- 与 Bridge / LTFP 的交互

#### `cloud-bridge/`
必须谨慎处理：

- Agent 接入
- 路由和资源分配
- 配置兼容性
- 管理台前后端联动

#### `apps/dev-agent/`
必须谨慎处理：

- UI 状态语义
- Tauri 宿主命令
- 本地通信协议
- 启动/关闭/错误反馈

#### `service-registry/`
必须谨慎处理：

- 注册发现语义
- watcher/client 兼容性
- 基础类型变更影响

---

## 8. 阶段五：验证确认

### 8.1 验证原则
验证必须遵循“最小必要、贴近改动、诚实说明”的原则。

不要：

- 没跑却说跑了
- 理论上能过就说已验证
- 用单点测试替代系统性风险说明

### 8.2 默认验证顺序
建议按以下顺序：

1. 目标目录局部检查
2. 目标模块测试
3. 目标模块构建
4. 必要时联调
5. 必要时文档与配置复核

### 8.3 Go 模块验证
本仓库有多个 Go module。  
应按实际模块分别处理，例如：

- `cd ltfp && go test ./...`
- `cd agent-core && go test ./...`
- `cd cloud-bridge && go test ./...`
- `cd service-registry && go test ./...`

### 8.4 前端/Tauri 验证
对于前端或桌面端项目，应先检查 `package.json` 脚本，再按需执行：

- 类型检查
- lint
- test
- build

涉及 Tauri 宿主的改动时，还应明确是否进行了真实桌面端验证。

### 8.5 未执行项必须透明说明
若没有执行以下验证，必须明确写出：

- 联调未做
- 真机未做
- Windows/Linux 平台验证未做
- 旧版本兼容性验证未做
- 构建未做

---

## 9. 阶段六：文档同步与结果总结

### 9.1 何时必须同步文档
当修改影响以下内容时，应同步更新文档：

- 技术方案
- 协议设计
- 配置说明
- 测试矩阵
- 发布/回滚说明
- 管理后台说明
- 本地通信模型说明

### 9.2 结果总结的标准结构
每次完成任务后，结果总结至少应包含：

1. 修改目标
2. 影响范围
3. 核心改动
4. 风险与兼容性说明
5. 已执行验证
6. 未执行验证
7. 已更新或待更新的文档

---

## 10. 不同任务的推荐协同模式

### 10.1 文档评审类
推荐流程：

1. 先读文档
2. 提炼目标和边界
3. 找问题点
4. 给出风险与可执行建议
5. 必要时再给落地方案

### 10.2 协议设计类
推荐流程：

1. 先读已有协议文档
2. 梳理当前语义
3. 识别兼容性风险
4. 形成计划
5. 再进入代码实现

### 10.3 运行时 bug 修复类
推荐流程：

1. 缩小问题范围
2. 锁定目标模块
3. 局部修改
4. 局部验证
5. 输出风险与未覆盖项

### 10.4 UI / Tauri 实现类
推荐流程：

1. 先确认页面目标与状态模型
2. 再确认本地通信边界
3. 分层修改前端与宿主
4. 做类型/构建/联调验证
5. 同步 UI 交互说明

---

## 11. 协同过程中的升级条件

当任务在执行过程中出现以下情况，应从“直接实现”升级为“先补计划再继续”：

- 发现实际影响多个模块
- 发现需要改协议或状态机
- 发现要动配置结构
- 发现要改前后端契约
- 发现要联动 Tauri 与 Agent Core
- 发现文档与代码现状不一致

此时不得继续按低风险任务处理。

---

## 12. 完成定义（Definition of Done）

一个任务完成，不等于“代码写完”。

默认完成标准包括：

1. 目标问题已被处理
2. 修改范围受到控制
3. 风险点已说明
4. 必要验证已执行或已明确缺口
5. 必要文档已同步或已列出待补项
6. 输出总结完整、可追踪

---

## 13. 本项目中的协同禁区

以下行为默认禁止：

- AI 擅自扩大任务边界
- 未经说明改协议语义
- 未经说明改状态机推进逻辑
- 未经说明改配置结构或默认值
- 直接改 `dist`、`node_modules`、`bin`
- 未检查兼容性就改 Agent/Bridge 协同逻辑
- 没跑测试却宣称已验证
- 用大规模重构替代问题定位

---

## 14. 实用工作准则

在本项目中，优先级固定如下：

1. 正确性
2. 兼容性
3. 边界清晰
4. 最小修改
5. 可验证性
6. 可维护性
7. 实现优雅性

如果“更优雅”的方案会导致：

- 更大影响面
- 更高兼容性风险
- 更低可验证性

则不优先采用。

---

## 15. 建议的日常使用方式

推荐把本项目协同方式固定为：

- 根 `AGENTS.md`：全局行为边界
- 模块级 `AGENTS.override.md`：局部约束
- `PLANS.md`：复杂任务计划模板
- `docs/AGENT-WORKFLOW.md`：人机协同流程说明

这样做的目的，是让所有复杂任务都遵循同一套节奏：

先识别边界，  
再规划方案，  
再实施修改，  
再验证与同步。
