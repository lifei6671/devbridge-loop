# AGENTS.override.md

## 1. 文档定位

本文件用于约束代理在 `agent-core/` 目录内工作的方式。

`agent-core` 是 Agent 侧核心运行时模块，负责承载：

- Agent 主程序入口
- Agent 运行时逻辑
- 事件机制
- 协议探测
- 若干基础能力

在本目录内工作时，必须优先保证：

1. 运行时正确性
2. 生命周期清晰
3. 与 Bridge / LTFP 的兼容性
4. 资源回收完整
5. 不破坏本地运行稳定性

---

## 2. 模块边界认知

### 2.1 目录职责
主要目录含义如下：

- `cmd/agent-core/`：可执行入口与启动装配
- `runtime/agent/`：Agent 核心运行时
- `pkg/events/`：事件定义与分发相关
- `pkg/protodetect/`：协议探测能力
- `pkg/tsbase62/`：基础编码能力

### 2.2 边界原则
在本模块内工作时：

- Agent 运行时逻辑优先保留在 `runtime/agent`
- 基础通用能力优先保留在 `pkg/*`
- 不要把本应属于协议库的能力塞进 `agent-core`
- 不要把本应属于上层 UI/Tauri 的逻辑下沉进 Agent Core

---

## 3. 工作原则

### 3.1 先判断问题类型
修改前先判断属于哪类任务：

1. 启动与装配问题
2. 长连接/会话问题
3. 协议探测问题
4. 事件分发问题
5. 本地资源或生命周期问题
6. 与 Bridge / LTFP 联动问题

其中第 2、3、5、6 类默认按中高风险处理。

### 3.2 优先局部修复
若问题只存在于某个运行时分支或某个探测流程，不要轻易扩散为全模块重构。

### 3.3 不引入隐式复杂度
不要为了抽象美观而：

- 额外引入层层接口
- 把简单控制流改成隐式状态机
- 大量创建后台 goroutine 却不清晰管理其退出

除非得到明确需要重构的任务。

---

## 4. 运行时与连接管理规则

### 4.1 `runtime/agent` 属于高敏感区
修改 `runtime/agent` 时，必须特别关注：

- 启动时序
- 建连/断连/重连
- 上下游通信
- 错误恢复
- 资源回收
- 本地状态同步

### 4.2 涉及连接时必须检查
若改动涉及长连接、流式通信、保活、会话绑定或断线重连，必须检查：

1. 初始连接是否仍然可建立
2. 失败重试是否存在风暴风险
3. 断开时是否会泄漏 goroutine / fd / channel
4. 是否存在重复注册、重复订阅、重复心跳
5. 关闭时是否能正确退出

### 4.3 错误路径必须视为一等路径
不要只考虑 happy path。  
对错误路径至少要思考：

- 握手失败
- 中途断连
- 半连接状态
- 重复事件
- 网络抖动
- 服务端暂时不可用

---

## 5. 协议探测规则

### 5.1 `pkg/protodetect` 属于高风险性能区
协议探测往往处于入口热路径，修改时必须关注：

- 误判率
- 探测顺序
- 读取边界
- 超时控制
- 回退行为
- 额外开销

### 5.2 默认要求
- 不要无控制地阻塞读取
- 不要无限等待某类探测结果
- 不要让探测过程吞掉原始数据而无法回退
- 明确处理 HTTP / HTTPS / 其他协议的边界
- 若涉及多协议复用，必须定义清晰的失败路径

### 5.3 变更后必须说明
若修改了探测策略，输出中要说明：

1. 旧逻辑是什么
2. 新逻辑是什么
3. 误判/回退行为是否变化
4. 是否可能影响已有端口复用策略

---

## 6. 事件机制规则

### 6.1 `pkg/events` 的改动必须谨慎
事件一旦被多个调用方依赖，语义变化会扩散很快。  
修改时必须检查：

- 事件名/事件类型是否变化
- 事件触发时机是否变化
- 是否会导致重复消费或漏消费
- 是否需要同步修改观察者/监听器

### 6.2 不滥用事件
不要把原本简单直接的调用链，改造成复杂事件链，除非任务明确要求。

---

## 7. 与 LTFP / Bridge 的协同规则

### 7.1 不在本模块随意重定义协议语义
涉及协议消息、状态、会话、协商等语义时，应优先遵循：

- `ltfp/` 的定义
- 既有文档
- 已有调用契约

### 7.2 改联动逻辑时必须考虑对端
若修改 Agent Core 与 Bridge 的交互行为，必须显式说明：

1. Agent 端改了什么
2. Bridge 端是否需要同步
3. LTFP 是否受影响
4. 是否存在兼容性断点

---

## 8. 测试与验证规则

### 8.1 Go 验证优先级
默认优先考虑：

1. 目标包测试
2. `agent-core` 模块内 `go test ./...`
3. 必要时入口构建验证

### 8.2 探测类改动
若改了 `pkg/protodetect`，应优先验证：

- 成功识别场景
- 误判场景
- 超时/失败场景
- 数据未被破坏的回退场景

### 8.3 生命周期类改动
若改了连接管理、重连、关闭流程，应特别说明是否验证过：

- 启动
- 重连
- 停止
- 异常中断
- 重复触发

### 8.4 未跑检查必须明说
若没做集成联调、真实网络场景验证或对端协同验证，必须明确说明。

---

## 9. 文档同步要求

若改动影响以下内容，应考虑同步更新仓库根 `docs/` 中相关方案：

- Agent 行为模型
- Agent 与 Bridge 协同
- Tauri 与 Agent 本地通信
- 协议探测策略
- 本地运行行为
- 错误恢复和重连机制

---

## 10. 完成任务后的输出要求

至少说明：

1. 修改目标
2. 影响目录
3. 是否涉及连接、探测、事件、生命周期
4. 核心改动
5. 风险点
6. 已执行验证
7. 未覆盖的联调或真实网络验证项

---

## 11. 明确禁止的行为

禁止：

- 把 UI 层逻辑塞进 Agent Core
- 未说明风险就改连接/重连/关闭逻辑
- 在热路径上无说明增加明显开销
- 用复杂事件链替代直接调用却不说明收益
- 不检查 Bridge/LTFP 影响就擅自更改交互行为
